# Spec: Named Skins Confidence And Recovery Loop

Triage: `ready-for-agent`

Depends on: [Named Skins Experience And Quality Loop](./named-skins-experience-loop.md)

## Problem Statement

The named-skins baseline is technically complete: Tension, Relay, and Field share a semantic-token contract, authenticated preferences synchronize across devices, offline changes reconcile, startup applies the correct account projection, and focused tests cover the contract. The remaining product gap is confidence at the moment of choice and recovery when something goes wrong.

The current picker uses abstract color swatches that do not show how operational states, Markdown, code, forms, or destructive actions will look. Selecting a skin immediately changes and persists it, while the confirmation only says that settings were saved. Diagnostics exist in the shared appearance contract but are not exposed to users or support. This leaves experimentation less reversible than it should be and makes rare synchronization failures harder to resolve.

Named skins should now enter maintenance mode. The next investment must make the existing choices easier to evaluate, undo, and diagnose. It must not expand into a theme marketplace or create more downstream surface ownership.

## Goals

- Let a user evaluate the meaningful differences between all three skins before committing a change.
- Make every explicit appearance change immediately reversible without losing the user's previous account preference.
- Turn sync and invalid-value failures into a user-visible recovery path with privacy-safe support evidence.
- Keep visual and accessibility coverage enforceable as upstream surfaces change.

## Non-Goals

- A fourth skin, arbitrary color controls, typography controls, density controls, or user-authored themes.
- Per-workspace skins or appearance-driven business behavior.
- A public theme gallery, sharing flow, or marketplace.
- Sending routes, page content, workspace identity, or arbitrary browser state in diagnostics or analytics.

## User Stories

1. As a user, I want each skin preview to show realistic status, text, code, selection, and action semantics, so that I can judge usability before switching.
2. As a user, I want to undo a skin or mode change from its confirmation, so that experimentation is safe.
3. As a user, I want reset to show the exact product defaults before I confirm it, so that reset is not ambiguous.
4. As a user with a sync failure, I want to know whether my current choice is local, pending, or synchronized and what action will recover it.
5. As a support engineer, I want the user to copy a bounded appearance diagnostic snapshot, so that I can diagnose account, adapter, and token-version mismatches without user content.
6. As a release owner, I want visual coverage to follow representative component states rather than a growing list of pages, so that upstream layout changes do not multiply downstream maintenance.

## Product Requirements

### Semantic Preview

- Replace decorative preview marks with a compact semantic sample containing primary and muted text, selection, success, warning, destructive, focus, and code/editor tokens.
- Preview cards render from the same semantic tokens used by the application. They may not duplicate literal colors in component code.
- Browsing a preview does not persist a preference. Selection remains an explicit click, keyboard activation, or touch action.
- The preview remains legible at 200% zoom, in forced-colors mode, with reduced motion, and with long localized labels.

### Reversible Changes

- Every explicit skin, light/dark/system, or reset action captures the previous complete `AppearancePreferences` value before applying the optimistic local update.
- The success notification offers one bounded Undo action. Undo is a new explicit preference write with its own timestamp; it never rewinds server state blindly.
- A newer explicit change invalidates an older Undo action. Cross-tab and cross-device changes are never overwritten by a stale Undo.
- Reset confirmation names the default skin and appearance. Reset retains the same offline-first and retry behavior as an ordinary selection.

### Recovery And Diagnostics

- The settings surface explains `local-only`, `pending`, `synced`, and `failed` states in plain language and exposes Retry only where it can make progress.
- After repeated failure, expose Copy diagnostics. The snapshot is generated by the existing shared diagnostics contract and includes only requested and resolved appearance, skin, adapter source, token-contract version, accessibility environment flags, sync state, and bounded error class.
- Copying diagnostics is local UI behavior. The product does not upload the snapshot automatically.
- Invalid stored preferences recover to a valid value, notify the user once, and include the recovered field in diagnostics and bounded analytics.

### Maintenance Contract

- Define a representative state fixture shared by token, contrast, and screenshot checks. It covers text tiers, form controls, focus, selection, status, charts, Markdown, code, overlays, and destructive actions.
- Release evidence uses this fixture for all six skin/mode combinations plus platform-specific smoke views. New upstream pages inherit tokens and do not automatically add downstream screenshots.
- Raw-color, missing-token, contrast, startup-flash, and hydration checks remain release gates.

## Technical Decisions

- Extend the existing appearance domain and adapter interfaces; do not introduce a second preference store.
- Keep React Query and authenticated user preferences authoritative for server state. The local adapter remains the startup and offline projection.
- Implement Undo as a compare-before-write operation against the expected optimistic preference timestamp. If the value changed elsewhere, leave the newer value intact and explain that Undo expired.
- Keep diagnostic serialization in `packages/core/appearance`; platform views only request and copy the bounded snapshot.
- Keep the preview fixture in shared UI tokens/primitives so Web, Desktop, Docs, and Mobile adapters consume the same semantic contract without sharing platform layout.

## Acceptance Criteria

- A user can compare all three skins without changing the persisted preference, select one, and undo the selection without a reload.
- A stale Undo cannot overwrite a newer local, cross-tab, or server preference.
- Failed synchronization preserves the selected local appearance, shows Retry, and exposes a copyable bounded diagnostic snapshot after repeated failure.
- Reset identifies and restores `tension` plus `system`, works offline, and synchronizes after reconnect.
- The semantic fixture passes token completeness and WCAG 2.2 AA checks for all required combinations.
- Diagnostics and analytics type contracts make content, routes, workspace identifiers, and arbitrary properties impossible to submit.
- Existing startup, account isolation, offline reconciliation, forced-colors, reduced-motion, keyboard, and screen-reader behavior does not regress.

## Metrics

- Primary: percentage of appearance changes retained for 28 days without reset or immediate Undo.
- Supporting: preview-to-selection rate, Undo rate, reset rate, sync failure recovery rate, invalid-value recovery rate, and appearance-related support incidents.
- Guardrails: first-paint mismatch, hydration warning, layout shift, contrast violation, raw-color count, and upstream merge conflicts attributable to appearance code.
- Stop rule: do not add another skin unless existing adoption, retention, full contract coverage, and maintenance-cost evidence justify it.

## Delivery Plan

1. Ship the shared semantic preview fixture and replace abstract picker previews.
2. Add compare-before-write Undo and explicit reset confirmation.
3. Expose bounded recovery diagnostics and complete failure-state copy.
4. Consolidate the release visual matrix around the representative fixture and move the feature to maintenance ownership.
