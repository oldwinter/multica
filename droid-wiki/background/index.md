# 分支背景与下游维护

本仓库是 Multica 的下游 fork：

- 下游仓库：`oldwinter/multica`
- 上游仓库：`multica-ai/multica`
- 本地惯例中，`origin/main` 表示已发布的下游主线，`upstream/main` 表示上游主线。

这个背景会直接影响功能归属、冲突处理和数据库迁移。下游并不是只在上游代码末尾追加补丁：Room、Twin / LM Wiki、命名皮肤、部分搜索与任务增强、Skill Evolution 等能力会与上游共享 handler、service、共享包和迁移目录。

## 权威维护记录

[上游同步账本](../../docs/downstream/upstream-sync.md)记录：

- 历次同步基线和冲突；
- 哪些目录或行为由下游主动维护；
- 已发布迁移的兼容身份；
- 冲突解决和验证规则；
- 下一次同步前需要保留的历史上下文。

本章是该账本的导航和解释，不替代账本。执行实际同步时应读取账本的最新版本，并使用仓库的 `multica-upstream-sync` skill。

## 为什么要同时看两条主线

同步不能只比较当前工作分支和 `upstream/main`。`origin/main` 可能包含已发布的下游提交、迁移和冲突解决；漏掉它会产生“源代码看似合并成功，但下游用户的迁移账本或功能被回退”的风险。

推荐的心智模型是三方协调：

```text
upstream/main ── 上游产品变化
      │
      ├── 当前同步分支 ── 冲突解决、生成物与验证
      │
origin/main   ── 已发布下游行为与迁移身份
```

## 维护原则

1. **按意图合并，不机械拼接冲突块。** 先理解双方生命周期、权限和数据约束，再选择最终行为。
2. **下游功能尽量拥有叶子模块。** 在上游稳定的注册点接入，减少共享核心文件的长期冲突。
3. **每完成一项下游功能就尽早同步。** 不要在一串本地功能后一次性吞并大量上游变化。
4. **迁移身份是已发布协议。** 文件名 stem、执行内容和既有账本必须一并考虑。
5. **生成物从源重新生成。** SQL 冲突先解决 query 源，再运行 sqlc；不要手工合并生成的 Go。
6. **记录验证对象。** 新数据库通过不代表已有下游账本可以升级，反之亦然。
